The Token Broker

An agent can now hold a real third-party token for a person — but only after that person has linked the provider and consented to that specific agent. The broker owns the lease, the scope-down, and the audit trail. Nothing else can hand out a credential.

Shipped · 2026-08-07 grant-acquisition token-brokering per-agent-consent

Prokura is an open-source reference implementation of agentic identity — the plumbing that lets an AI agent act on your behalf without ever holding your passwords or your provider refresh tokens. It is assembled from Keycloak, OpenFGA, and OpenBao. ("Prokura" is the civil-law term for a registered power of attorney.)

M0 stood up the stack. M1 taught agents to exchange a user's login for a delegated token. M2 is the heavy one: it turns that delegated token into an actual, short-lived GitHub/Google-style token — through a broker that is the single, auditable choke-point for every third-party credential.

The shape of it

Who is trusted, and who is kept out

Five components sit behind the compose network. Three of them form the trusted computing base — they can mint, broker, or gate credentials. The agent is deliberately outside it: the most it can ever present is a token addressed to the broker, for a grant it has been individually consented to use.

How it works

From a login to a scoped provider token

Three ceremonies, run once each and then reused. Every step below is enforced in code and covered by a test.

01

Link the provider

The user runs Keycloak's kc_action=idp_link:acme flow. Keycloak brokers to the mock acme realm, the user approves, and Keycloak stores the provider's refresh token under their identity. The broker never runs its own OAuth — it consumes what Keycloak brokered.

02

Import the grant

The broker retrieves the stored credential and moves it into OpenBao at secret/grants/{user}/{provider}. From that moment the long-lived credential exists only in the vault — never in a response, a log, or the broker's database.

03

Consent to one agent

On an authenticated screen the user approves a specific agent for that grant. Approval writes exactly one OpenFGA tuple: agent can_use grant. The broker is the sole writer and refuses any write where the agent's operator isn't the grant's owner.

04

Hand out a token

The agent presents a broker-audience token and asks for a provider token. The broker runs the chain in order — 1 signature2 aud=token-broker3 scope ⊆ grant4 can_use — then refreshes against the provider and returns an access token capped at 900 seconds. Any failure is a 403 before the provider is ever contacted. The refresh token stays in the vault.

Decisions & what we learned

The spike earned its keep

M2 opened with a throwaway spike proving the linking flow end-to-end before a line of the broker was written. It surfaced a stack of non-obvious Keycloak behaviour — each one is now baked into the committed realm so the whole thing rebuilds from a clean docker compose down -v && up.

Decision

The mock provider is a whole Keycloak realm, not a stub

A second realm, acme, stands in for GitHub/Google. It exercises the real brokering and stored-token machinery with zero external credentials — so wiring a real provider later is a config swap, not a rewrite.

Learned

Account-linking is refused unless three conditions are met

Keycloak's idp_link returns not_allowed unless the user holds manage-account, the request forces a fresh login with prompt=login, and a Keycloak-26 "do you want to link?" confirmation is accepted. None of that is in the docs' happy path.

Learned

The read-token role is not auto-granted for existing users

addReadTokenRoleOnCreate only fires when a brokered user is created. Linking to a pre-existing account skips it — so the role, plus a custom client-role mapper (this realm had dropped Keycloak's built-in roles scope), had to be added explicitly.

Learned

Browser and back-channel URLs must be split

Keycloak listens on keycloak:8080 inside the network but is pinned to localhost:8180 for issuers. Realm-to-realm brokering only works when the identity provider's authorization URL uses the browser host and its token/JWKS URLs use the back-channel host.

Decision

The broker re-exchanges the token itself — agents never get read-token

Giving the agent the credential-read capability would let it bypass the whole broker. Instead the broker performs its own RFC 8693 exchange as the confidential token-broker client to obtain read-token, keeping that power inside the trust boundary.
