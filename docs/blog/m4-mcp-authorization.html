Milestone 04 · Build log

An authorization server a real agent connects to

M0–M3 built the whole delegation chain, but a library drove it. M4 makes it reachable by any standard MCP client — it discovers the server, registers itself, logs the user in, and then, through MCP tools, obtains a brokered provider token and performs a human-approved action. Keycloak becomes the MCP authorization server; the trigger for approval moves onto the resource server.

Shipped · 2026-08-07 mcp-authorization MCP 2025-06-18 RFC 9728 · 8414 · 7591

This is the headline. So far every flow was driven by Prokura's Python SDK and the test harness. M4 is where Prokura stops being "a library you call" and becomes "an authorization server a real agent connects to." The client is standard MCP: it hits a 401, follows the pointer to protected-resource metadata, finds Keycloak, registers dynamically, runs OAuth 2.1 + PKCE, and calls tools — the exact handshake Claude and other MCP clients use.

With dynamic registration on, the security story becomes explicit: any client can register. Registration by itself grants nothing — per-agent consent (M2) gates provider access and human approval (M3) gates sensitive actions. Consent and approval, not registration, are the gates.

The shape of it

The MCP server wears two hats

One new service joins the stack. The MCP server is an OAuth 2.1 resource server — it publishes RFC 9728 metadata, challenges unauthenticated requests, and validates the token audience — and a minimal MCP server whose tools drive the chain. Keycloak is the authorization server: it serves RFC 8414 metadata and permits RFC 7591 dynamic registration.

How it works

From a cold 401 to a human-approved send

01

Discover, then register

An unauthenticated POST /mcp returns 401 with WWW-Authenticate: Bearer resource_metadata="…". The client fetches that RFC 9728 document, finds the Keycloak realm named as its authorization server, and registers dynamically (RFC 7591) — a client id with no operator in the loop.

02

Log in with OAuth 2.1 + PKCE

The client runs the authorization-code flow with PKCE and the RFC 8707 resource parameter. Keycloak doesn't reflect resource into the audience (a real gap) — so a realm-default client scope binds aud=mcp-server instead. The MCP server validates it; a wrong-audience token is challenged, not served.

03

A tool call drives the chain — without passthrough

On tools/call, the MCP server exchanges the inbound token (RFC 8693, as the confidential mcp-server client) for a broker- or tools-audience token. The inbound MCP token is never forwarded. get_provider_token reaches the broker (consent-gated); send_email reaches the gated action.

04

The resource server demands approval

The first send_email arrives with no action token. Instead of running, the tools-API registers the exact action it observed and refuses with a 428 approval_required challenge. The client drives CIBA for that reference, a human approves what the server stored, and the retry executes once.

Decisions & what we learned

Where the standard met the implementation

Decision

Keycloak is the MCP authorization server

RFC 8414 metadata already worked; anonymous DCR was blocked only by the Trusted Hosts policy. We opened it for localhost redirect URIs (which OAuth 2.1 requires anyway) and baked the policy into the realm — so a real MCP client registers with no operator involvement.

Learned

The RFC 8707 resource parameter is not reflected into aud

The spike confirmed it against the running image: the audience came back null. So we bound audience the M1/M2 way — an mcp-audience client scope (an audience mapper), made a realm default so every DCR client carries aud=mcp-server. The client still sends resource per spec; binding just doesn't depend on it.

Decision

Never forward the inbound token — exchange for every hop

The MCP server holds an aud=mcp-server token and needs aud=token-broker / aud=agent-tools-api downstream. It exchanges (RFC 8693) as its own confidential client. Presenting the raw MCP token to the broker is refused — proof the passthrough never happens.

Learned

The approval trigger belongs on the resource server

M3 left the trigger with the agent. M4 moves it: the tools-API refuses an un-approved call with a 428 and registers the action it actually saw. The agent identity for consent is the mcp-server client (exchange sets azp to the requester) — an honest, documented trade-off over per-DCR-client consent.

Run it yourself

Drive the whole chain as a real MCP client would

The tests are a scripted, spec-compliant MCP client: discover → register → OAuth 2.1 + PKCE → tools/list → a consent-gated brokered token → a reactive, human-approved send. A real client uses the same standard steps.

your shell · repo root · stack up, venv active (see M0 / M1)
$ docker compose up -d

# discovery (401 -> PRM -> AS metadata) -> DCR -> OAuth 2.1 + PKCE
# -> aud=mcp-server -> tools/list; wrong-audience token refused
$ pytest tests/smoke/test_mcp_authorization.py -v

# through MCP tools: a brokered provider token, then a reactive
# challenge -> CIBA -> approve -> retry -> mail in Mailpit
$ pytest tests/smoke/test_mcp_chain.py \
         tests/smoke/test_reactive_approval.py -v

# the MCP row on the delegation dashboard
$ open http://localhost:3001/d/prokura-delegation

Verified by looking

What we confirmed

  • ✓A cold POST /mcp returns 401 + resource_metadata, and that RFC 9728 document names Keycloak as the authorization server.
  • ✓A dynamically-registered client completes OAuth 2.1 + PKCE and its token carries aud=mcp-server; a wrong-audience token is refused at the MCP boundary.
  • ✓Through MCP tools, a consent-gated brokered token is returned and a human-approved email lands in Mailpit — the reactive challenge → CIBA → retry path.
  • ✓The inbound MCP token is refused downstream — it is never forwarded; each hop is a fresh RFC 8693 exchange.
  • ✓The flow is one linked trace (mcp → keycloak → tools-api → approval) with the same correlation id in live Loki audit and on the dashboard's MCP row.
