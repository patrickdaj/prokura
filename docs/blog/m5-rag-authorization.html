Milestone 05 · Build log

Retrieval that stops at the user's permission line

M1–M4 proved the action side of agentic identity — delegated exchange, brokered tokens, human approval, all through MCP. M5 proves the data side: an agent retrieves only the documents the querying user is entitled to see, enforced by evaluating OpenFGA as the end user, never as the agent. The proof is adversarial — a protected doc is the top embedding hit and still never leaks.

Shipped · 2026-08-07 rag-authorization OpenFGA batch_check pgvector · RFC 8693

This is the confused-deputy defense made concrete. A retrieval-augmented agent is a classic deputy: it holds powerful credentials and acts on a user's behalf. If it embeds a query, pulls the nearest documents, and hands them to the model, it will happily surface a file the user was never allowed to open. The fix is not a filter bolted on after — it is to make the authorization decision at retrieval time, as the user.

M5 adds one service: a RAG retriever that validates a token addressed to its own audience (aud=rag-server), derives the end user from it, and authorizes every candidate chunk against OpenFGA as user:{sub}. Agent identity alone gets nothing. It is reachable as the rag_search MCP tool — the same surface as M4 — so the demo trilogy (GitHub issues → gated email → ACL'd RAG) lands on one connection.

The shape of it

The retriever authorizes as the end user

The RAG retriever is a resource server like the broker and tools-API: it accepts only a token minted for its own audience. The rag_search MCP tool exchanges the inbound token (RFC 8693) for aud=rag-server — never forwarding it — and the retriever runs an OpenFGA batch_check for document:{id} viewer user:{sub} across the candidate set. Only authorized chunks survive.

How it works

From a query to only-what-you-may-see

01

Exchange for the retriever's audience — no passthrough

On tools/call rag_search, the MCP server exchanges the inbound token (RFC 8693, as the confidential mcp-server client) for aud=rag-server. The exchange preserves the end user's sub while azp becomes mcp-server. The inbound MCP token is never forwarded — presenting it to the retriever directly is refused.

02

Embed, then pull the nearest candidates

The retriever validates aud=rag-server (the F2 defense), embeds the query with a local, offline, deterministic vectorizer, and asks pgvector for the top-K nearest chunks. This is the candidate set — ranking only, no authorization yet. The protected doc, if it matches, is right here at the top.

03

Authorize the candidates as the end user

One OpenFGA batch_check asks, for each candidate, is user:{sub} a viewer? — the querying human, not the agent. Only chunks whose document the user may view survive into the answer. A retrieval with no end user, or a foreign-audience token, returns no chunks at all.

04

The top hit is filtered, not the tail

The corpus is seeded so a protected file (secret-roadmap, shared with alice only) is the #1 embedding hit for a crafted acquisition-timeline query. For bob it is the top candidate too — and it is dropped after ranking. allowed < candidates: the authorization decision, not the ranking, is what he sees.

Decisions & what we learned

Where the standard met the implementation

Decision

Authorize as user:{sub}, never as the agent

The whole point. The retriever derives the subject only from a token whose aud it validates as rag-server — never a caller-supplied id — and runs batch_check as that user. "Agent identity is insufficient" is a service-level test, not a convention: the agent's own aud=mcp-server token gets zero chunks.

Learned

pgvector isn't in postgres:17-alpine

The spike found CREATE EXTENSION vector fails on the stock image. The fix was a one-line image swap to pgvector/pgvector:pg17 (Postgres 17 + pgvector 0.8.6) — the vector store rides in the existing Postgres, adding no container. Verified with a real cosine top-K before a line of service code.

Learned

The FGA subject is the username, not the raw sub

The token sub is an opaque UUID; preferred_username is the stable id the broker and the whole OpenFGA model already key on (user:alice). So the retriever authorizes as user:{preferred_username} — the concrete, cross-service-consistent reading of the spec's user:{sub}.

Decision

Offline embedder; Drive-shaped manifest; live Drive parked

Embeddings come from a deterministic, no-secret vectorizer so the demo runs offline and the adversarial case reproduces byte-for-byte — the property under test is authorization, which a lexical embedder proves as well as a semantic one. Tuples are seeded from a Drive-shaped manifest; live Drive ingestion is parked to v1, and it changes only the tuple source — the filter is identical.

Run it yourself

Prove the leak that never happens

The tests drive the live stack as a real MCP client: they log in as alice and bob, call rag_search with the adversarial query, and assert alice retrieves the protected doc while bob provably cannot — even as his top hit — and that the inbound MCP token is never forwarded downstream.

your shell · repo root · stack up, venv active (see M0 / M1)
$ docker compose up -d   # rag seeds its corpus + FGA tuples at startup

# authorized retrieves; unauthorized doesn't — even as the #1 hit;
# foreign-audience / no-identity calls return no chunks
$ pytest tests/smoke/test_rag_authorization.py -v

# rag_search through MCP: end-user sub preserved, only that user's
# chunks returned, inbound MCP token not forwarded downstream
$ pytest tests/smoke/test_rag_mcp.py -v

# the RAG row on the delegation dashboard
$ open http://localhost:3001/d/prokura-delegation

Verified by looking

What we confirmed

  • ✓An authorized user retrieves a protected document through rag_search; an unauthorized user does not — even though it is the top embedding hit (allowed < candidates).
  • ✓The retriever authorizes as user:{sub} from a validated aud=rag-server token; a foreign-audience or identity-less call returns no chunks.
  • ✓The inbound MCP token is refused downstream — rag_search exchanges for rag-server and never forwards it.
  • ✓Ingestion writes a document's FGA tuples before its chunks are queryable; a document with no tuples is visible to no one.
  • ✓The flow is one linked trace (mcp → rag → openfga) with the same correlation id in live rag_audit and on the dashboard's RAG row; a clean-slate down -v && up reproduces it.

Where this leaves Prokura. The delegation story is complete end to end: an agent connects over MCP, exchanges for exactly the audience each hop needs, gets consent-gated tokens and human-approved actions, and now retrieves only the data the user may see — every hop observable as one trace. Live Google Drive ingestion is the named next step; the enforcement path it plugs into is already built and tested.
