Milestone 09 · The kill switch

How fast can you make an agent stop?

It's the first question a security team asks — and until now Prokura's honest answer was "up to fifteen minutes." M8 let you revoke a delegation; the console said so itself: effect on the agent's next token request. M9 turns that into a measured number of milliseconds. A per-grant revoke now deletes the consent tuple and writes a broker deny-list entry and emits a CAEP signal — instant, scoped, and impossible to slip past with a fresh token. The one thing we can't shorten — a provider token already in the agent's hand — we bound and report, rather than pretend we killed it.

Shipped · 2026-08-10 add-instant-revocation deny-list + CAEP/SSF ADR-0024

Three facts made "stop" slow, and we measured each. The broker already re-checks the can_use tuple on every hand-out, so a deleted tuple denies the next request in ~36 ms — that part was already instant. But a provider access token already issued stays valid at the provider until its TTL (900 s), and an agent holding a refresh token could mint fresh tokens and keep going. So "instant revocation" is really: deny the next hand-out (done), make the already-issued token's window small and honest, and — for a full stop — stop the agent re-acquiring authority at all.

The headline

Per-grant revoke: a tuple delete and a deny-list and a signal

Clicking Revoke now does three things in one broker call. It deletes the can_use tuple (the durable consent state). It writes a deny-list entry — a propagation-free "stop now" that the hand-out chain checks on every request, before the provider is contacted, independent of any OpenFGA read consistency. And it emits a CAEP Security Event Token so revocation is a signal other systems can consume, not just an internal delete. It is scoped: the agent's Keycloak session and its other grants are untouched.

The deny-list is what makes re-acquisition impossible: even a brand-new user token can't get the revoked grant back, because the broker denies it before it ever calls the provider. So a fresh token is not a way around revocation — no Keycloak session surgery is even required to protect the revoked grant.

Honest about the one thing we can't kill

The in-flight residual, named — not pretended away

A provider access token already in the agent's hand keeps working at the provider until it expires — the mock acme provider has no revocation endpoint, and pretending otherwise would be a lie the whole project exists to avoid (ADR-0003). So M9 bounds the hand-out TTL to 120 s and reports the residual: "any token already issued expires within ≤ 120 s." New authority is denied in milliseconds; the small remaining window is disclosed, not hidden. Real providers (Google, GitHub) that support token revocation close even this — that's M12.

For a full stop — "de-delegate this agent entirely" — the agent-wide kill additionally revokes the agent client's Keycloak sessions and offline/refresh tokens for that user (a targeted DELETE users/{id}/consents/{client}, needing only manage-users), so a re-mint returns 400 invalid_grant. It is scoped to the agent: the human's own sessions are never touched. The spike proved the exact API and the minimal role before a line of service code.

The answer, on the dashboard

"How fast can you make an agent stop?" — with a number

Every revoke records a prokura.revocation.stop_ms metric, joinable to its trace and audit line, and the operator dashboard graphs it. The security team's first question now has a live answer instead of a shrug.

Spike-first paid off. Before any code, spike/kill-switch measured the three revocation paths against the live stack and proved the Keycloak revocation API + minimal role. The design turned on those numbers — including the honest residual — not on a guess.
