The human in the loop

Some actions are too important to leave to prior consent. M3 makes a sensitive action pause for a person — who approves it in a trusted screen that shows exactly what will run, and gets back a credential that works once, for that action only. No agent-written text ever reaches the human; no Java plugin is needed.

Shipped · 2026-08-07 human-approval CIBA agent-sdk

M2 gave an agent a scoped third-party token, gated on consent the user gave earlier. But "send this email", "move this money" deserve a decision at the moment they happen. M3 is Prokura's Flow C: the agent asks, the action blocks, a human decides, and only an approved-and-unmodified action can run — exactly once.

The transport is Keycloak's own CIBA (Client-Initiated Backchannel Authentication) over its built-in HTTP channel — the thing the M0 foundation spiked specifically to prove no custom Java extension would be needed. M3 turns that spike into a real approval service that joins the trusted core.

The shape of it

An action that stops and waits for a person

Two new services join the stack. The approval service is trusted — it holds the payload, renders it to the human, and issues the single-use token. The tools-api is the resource server that actually performs the action, but only after the approval service confirms the exact action was approved and hasn't run before.

How it works

From "please send this" to "sent, once"

01

Register the exact action

The agent registers a structured {action, params} with the approval service, which records a hash and returns a reference ID. That reference — never agent prose — becomes the CIBA binding message.

02

The action pauses on CIBA

Keycloak POSTs the request to the approval service's channel and the agent's call blocks. A notification (deep link + reference only) rings the user's phone; the decision itself happens elsewhere.

03

A person approves what they can see

In an authenticated screen the user sees the action and parameters as stored by the service — "Wire $4,200 to vendor #8821", not whatever the agent claimed. Approve relays the decision to Keycloak; the agent's poll returns a token.

04

Run it once, exactly as approved

The tools-api checks the audience, then asks the approval service to verify the action hashes to the approved payload and to atomically consume the reference. Tamper with a parameter and it's refused; present it twice and the replay is refused.

Decisions & what we learned

Where the ceremony had to bend

Decision

No Java plugin — the built-in CIBA HTTP channel

M0 spiked exactly this so M3 wouldn't need a custom Keycloak extension. M3 just repoints the channel at the approval service; the delegation POST and decision callback round-trip as proven.

Learned

The reference ID does not ride on Keycloak's token

We verified against the running image: the CIBA binding message never surfaces as a claim, and adding a mapper would mean a Java SPI. So the approval service became the action-token authority — it issues and introspects the single-use token, keeping the binding in one trusted place.

Decision

The UI renders the service's payload, never the agent's words

The human approves what the service stored and hashed. This is the whole point of Flow C — you approve what will actually happen, not what an agent says will happen.

Learned

Notifications had to be provisioned to be inert

ntfy ships deny-all, so a publisher had to be created with write access to per-user unguessable topics only. The result is the intended property: a notification is a capability-free doorbell, and a spoofed publish is simply refused.

Verified by looking

What we confirmed

  • ✓The approval screen renders the service-held payload — checked in a real browser, agent text nowhere in sight.
  • ✓An approved action runs once and lands in Mailpit; a replay is refused and a tampered parameter is refused.
  • ✓Denial and the 30 s timeout both abort cleanly — the agent's poll errors and nothing runs.
  • ✓A notification leaks no parameters, and a spoofed publish is refused and inert.
  • ✓The audit trail reaches Loki with a correlation id joining register → approve → consume.

What's next. M4 is the headline: Keycloak as an MCP authorization server, so a real MCP client can drive this whole chain — login, consent, a brokered token, and a human-approved action — through standard tools.
