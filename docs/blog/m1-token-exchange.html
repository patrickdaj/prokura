Delegated Token Exchange

An agent turns your login into a delegated token — one that still says the action is you, records which agent is acting, carries only the scopes it asked for, and is addressed to exactly one recipient. This is the foundation every later milestone stands on.

Shipped · 2026-08-07 identity-delegation agent-sdk RFC 8693

Prokura is an open-source reference implementation of agentic identity — how an AI agent acts for you without ever holding your passwords. It is built from Keycloak, OpenFGA, and OpenBao. ("Prokura" is the civil-law term for a registered power of attorney.)

M0 stood up the stack and proved login works. M1 makes delegation real. When an agent needs to call something on your behalf, it doesn't reuse your login token — it exchanges it for a new one that is honest about who is really acting, and for whom.

The shape of it

One user token becomes many honest tokens

The agent never sends your original login onward. It exchanges it — once per recipient — for a downscoped token addressed to that recipient alone. A token minted for the tools API cannot be replayed at the broker, and vice versa.

How it works

The exchange, step by step

01

The agent holds a user token

The user logs into the confidential agent-app client. The agent now has a normal access token — sub=alice — but must not present it onward as if it were the user.

02

Exchange for a specific audience

The SDK calls Keycloak's token-exchange grant with a single target audience. Keycloak checks an explicit per-client, per-audience permission — no wildcards — and mints a new token.

03

The new token is attributable and downscoped

It keeps sub=alice (the action is still the user's), adds azp=agent-app (this agent is acting), carries only the requested scopes, and names the target in aud. Nothing is written to disk or logged.

04

The audience defense (F2-A)

A token addressed to the tools API is worthless at the broker. In M2 the broker rejects anything whose aud isn't token-broker — a defense this milestone sets up and proves.

The API

What an agent actually writes

The whole surface is one function. It is thin on purpose — httpx plus the standard library, no token cache, no secrets embedded.

prokura-py · exchange()
# turn the user's login into a token addressed to the broker
broker_token = exchange(
    user_token,
    audience="token-broker",   # F2-A: one recipient
    base_url=KEYCLOAK, realm="prokura",
    client_id="agent-app", client_secret=SECRET,
)
# broker_token: sub=alice, azp=agent-app, aud=[token-broker]

Decisions

Why it's built this way

Decision

Standard token exchange, not the legacy path

Keycloak 26's supported urn:…:token-exchange grant, verified against the pinned image rather than from memory — M0 taught us that config flags churn between versions.

Decision

Two explicit exchanges, never one multi-audience token

Each token stays honest about its single addressee. It's what lets the broker (M2) safely reject anything not addressed to it.

Decision

The SDK never persists a token

Tokens are in-memory, short-lived values. Nothing is written to disk, logs, or any cache that outlives the process — asserted by a test on every path.

Verified by looking

What we confirmed

  • ✓Exchanged tokens carry sub=user, azp=agent and only the requested scopes — decoded and asserted.
  • ✓An un-permitted audience raises ExchangeDenied, naming the audience — no token leaks out.
  • ✓The broker-audience token is accepted where a plain user token is refused (the F2-A defense).
  • ✓The delegated exchange appears as a linked, cross-service trace in the console.

What this unlocks. The broker-audience token minted here is exactly what M2 consumes: an agent presents it, and — if the user has linked the provider and consented to that agent — receives a scoped, short-lived third-party token in return.
