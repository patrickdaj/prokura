Milestone 06 · Threat model

The four ways in — and why each one closes

With the architecture frozen, we modeled it adversarially: assets, an explicit attacker model, trust boundaries, STRIDE for every flow, and an attack tree for each highest-value target. This is the findings story — the four scariest paths an attacker would take, and the specific control that breaks each. The headline: no High or Medium findings, three Low ones stated honestly, and the confused-deputy — the whole reason this project exists — provably dead.

Modeled · 2026-08-07 threat-model STRIDE · attack trees adversary-centric

A companion review asked “are the hard rules enforced?” and answered yes with evidence (see security-review.md). This one asks the opposite question — “what can an attacker actually do?” — and follows each answer to the control that stops it. The full model (assets, five STRIDE grids, disposition mapping, residual register) is threat-model.md; this post walks the four attack trees that matter most.

The attacker model is explicit. Every path below is attributed to a defined adversary: a compromised agent holding a valid user-delegated token, a self-registered MCP client, an on-network attacker (no mTLS between services), a malicious grant-linking user, or a curious insider. None can forge Keycloak's signatures, read OpenBao without the broker's scoped token, or write an authorization tuple except through broker code — and those boundaries are what the trees keep hitting.

The four trees

Where an attacker would push, and what pushes back

Target 1 · Token-broker compromise

Steal every provider credential at once

Path. Code-exec on the broker container → use its in-process OpenBao token → read secret/data/grants/* → every user's refresh credential. The broker is also the sole can_use writer, so the same foothold forges consent. This is the worst case, and we name it as such.

What bounds it. The broker's OpenBao token is scoped to grants/* only — no root, no other path. Refresh credentials never leave OpenBao except transiently in memory during a refresh, and never appear in a response, log, or audit line. The concentration itself is an accepted residual for a single-node reference; production splits it (isolation, per-tenant brokers, HSM-backed store). It is flagged as a trusted-code assumption so the other trees can reason about it. See M2.

Target 2 · Consent tuple forgery

Give my agent access to your grant

Path. Write a can_use tuple for the victim's grant directly in OpenFGA, or drive the broker's consent endpoint as the victim.

What breaks it. Both dead-end. The model uses can_use: [agent] direct assignment — no relation chaining to forge through — and only broker code writes it. The broker enforces operator == owner at write time: the consenting session must own the grant, and a cross-user write is refused and audited. The only residual is Target 1 (broker compromise) — a trusted-code assumption, handed forward, not hidden. See M2.

Target 3 · Approval spoofing / replay

Execute a sensitive action nobody approved

Paths. Forge the decision; spoof the notification; race the CIBA delegation receiver; replay an already-approved action. This tree is where the review's most interesting finding lives — SR-02: the /ciba/delegate receiver doesn't authenticate that the caller is Keycloak.

What breaks it — and the honest edge. Forging a decision fails: /decide needs the real user's authenticated session (sub == owner). Notifications are inert: ntfy is deny-all, per-user unguessable topics, no params in the payload. Replay fails: the action token is atomically single-use, and the tools-API hash-verifies the params against what was approved. And SR-02? A forged /ciba/delegate only lets someone who already knows the 96-bit reference win a once-only pending→delegated step — it cannot approve (the decision still needs the user, and Keycloak validates the delegation token on callback). Net impact: denial-of-service on one approval, not a forged one. Recommended fix for v1: authenticate the channel caller. See M3.

Target 4 · RAG confused-deputy

Make the agent hand over a file you can't see

Path. Craft a query so a protected document is the top embedding hit, let the high-privilege agent retrieve it, and read it out of the answer. This is the canonical deputy attack — the reason the whole project exists.

What breaks it. Authorization is evaluated as the end user, never the agent: after ranking, an OpenFGA batch_check with subject user:{sub} filters every candidate, so the top hit is dropped when the user holds no viewer tuple. Proven adversarially — the protected doc is the #1 candidate and still never reaches a non-viewer's answer (allowed < candidates). See M5.

Stated honestly

The three findings, and what we accept

Zero High/Medium doesn't mean zero findings — that would be theater. Three Low ones, and the residuals a non-production reference deliberately accepts:

Low · fix (v1)

SR-01 — error bodies echo library exception text

A malformed bearer token surfaces the underlying JWT/codec error string. Leaks implementation detail, no secret. Sanitize to a generic message.

Low · fix (v1)

SR-02 — /ciba/delegate is unauthenticated

Bounded to DoS of one approval by someone who already knows its unguessable reference (attack tree 3). Verify the caller is Keycloak.

Low · accepted residual

SR-03 — no size cap on the RAG query

Bounded by the offline, linear-cost embedder. Add an explicit input bound in v1.

Accepted residual

Non-production posture

No mTLS, dev-mode secrets, single-node, no rate-limiting, the broker as a concentrated point of trust. Each is listed with its production alternative — not implied to be mitigated.

The method, briefly

Three lenses on one system

M6 looks at the finished architecture through three non-overlapping lenses so nothing hides in the seams between them:

  • ◆Control-centric (security-review.md) — are the hard rules enforced? One security-baseline contract, evidence per invariant.
  • ◆Adversary-centric (this, threat-model.md) — what can an attacker do? STRIDE per flow, attack trees, every threat mapped to a control or an accepted residual.
  • ◆Decision-centric (adr/) — why does each control exist? One ADR per locked decision.

The takeaway. Every high-value path we could draw ends at a control we can point to — a signature check, a scoped token, a sole-writer invariant, an end-user authorization decision — or at a residual we name out loud. The confused-deputy, the attack this whole architecture exists to stop, is dead even when the protected document is the single best match for the query.
