Watch an agent act for a user — and stop exactly where it should

A single MCP client, holding only an aud=mcp-server token, walks the whole chain: it discovers the server, registers itself, logs the user in, gets a consent-gated third-party token, has a human approve a gated email, and runs a RAG query that returns only what the user may see. 01

Discover, register, log in

An unauthenticated POST /mcp returns 401 pointing at RFC 9728 metadata that names Keycloak. The client registers dynamically (RFC 7591), runs OAuth 2.1 + PKCE, and receives an aud=mcp-server token. tools/list then advertises the three tools that drive the chain.

MCP client · :8140/mcp
# POST /mcp with no token
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="…/.well-known/oauth-protected-resource"
# → discover Keycloak, register (RFC 7591), OAuth 2.1 + PKCE →
token.aud = "mcp-server"   sub = alice

# tools/list
[ get_provider_token, send_email, rag_search ]
What it proves: a real client reaches the server with the standard MCP handshake — no operator in the loop. → MCP surface deep-dive · M4 blog
02

Per-agent consent

Registration grants nothing. Before the agent can touch a user's third-party grant, the user consents to this specific agent — the approval writes the OpenFGA can_use tuple (the broker is the sole writer, enforcing operator == owner).

:8110/consent · authenticated
P R O K U R A

Allow this agent to use your grant?

AllowDeny
What it proves: consent — not registration — is the gate, and it is per-agent. → Brokering deep-dive · M2 blog
03

A brokered provider token

The get_provider_token tool exchanges the inbound token for an aud=token-broker one (never forwarding it) and calls the broker, which checks the grant, the requested scopes, and the consent tuple — then returns a short-lived access token only.

rag_search / get_provider_token result
# tools/call get_provider_token { provider: "acme" }
{
  "access_token": "eyJ…",
  "expires_in": 900,        // ≤ 15 min, always
  "scope": "read:acme"
  // no refresh_token — it never leaves OpenBao
}
What it proves: the agent gets a bounded access token; the refresh credential stays in OpenBao. → Delegation deep-dive · M1 blog
04

Human approval on a gated action

The first send_email arrives with no action token. The tools-API refuses with a 428 approval_required and registers the exact {action, params} it saw. A human approves that in the trusted UI (never agent-authored text); the retry executes once, and the mail lands in the Mailpit sink.

:8120 approval UI

from tools-api (single-use token consumed)
What it proves: the approved action is the one the server saw; the token is single-use and hash-bound. → Approval deep-dive · M3 blog
05

RAG that stops at the permission line

The rag_search tool embeds the query and pulls the top-K candidates from pgvector, then authorizes them against OpenFGA as the end user. The protected secret-roadmap is the #1 hit for both alice and bob — but bob holds no viewer tuple, so it is filtered after ranking.

alice · viewer
#1secret-roadmap0.68✓ shown
#2public-handbook0.09✓
#4shared-budget0.00✓
answer contains "Meridian acquisition"
bob · not a viewer
#1secret-roadmap0.68✕ filtered
#2public-handbook0.09✓
#3bob-notes0.09✓
answer never mentions "Meridian"
What it proves: the confused-deputy is dead — the top hit leaks to no one who lacks the tuple. candidates=4, allowed=3. → RAG deep-dive · M5 blog
