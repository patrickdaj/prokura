Flow C · human-approval deep-dive

A human approves the exact action — not the agent's word for it

Some actions need a person. When the agent calls send_email, the server refuses, stores the payload, and asks a human to approve what the server saw — rendered in a trusted surface, not from anything the agent wrote. Approval yields a single-use, hash-bound token; the action then runs exactly once. Every screen is captured live.

CIBA step-uptrusted renderingsingle-usehash-bound
01

The agent asks; the server refuses and registers the real action

The first send_email carries no approval. The resource server responds 428, stores the payload server-side, and returns a reference — no email is sent.

tool: send_email(...)
$ tool.send_email { to:"board@prokura.local", subject:"Q3 board update…", body:"…" }
428 {"error":"approval_required",
     "ref":"apr-722076c4e2e97d59e6f6769f"}   // payload stored server-side
What it proves: a sensitive action can't proceed on the agent's say-so; the server takes custody of the exact payload.
02

A human approves — in a trusted surface, on the server's payload

CIBA pushes the request to the user's device; they open the approval screen. The details are rendered by the approval service from stored data — the agent cannot influence what the human sees. Alice reads the real to/subject/body and clicks Approve.

localhost:8120 — trusted approval UI
What it proves: the human approves the action the server holds — not agent-supplied text — closing the substitution gap.
03

Approved → the agent runs it exactly once → the mail lands

With approval, the retry presents a single-use token; the tool verifies it against the stored hash and sends. Here is the delivered message in the Mailpit sink — matching the approved payload byte for byte.

localhost:8025 — Mailpit
What it proves: the agent really acts — but only the approved action, and only after a human said yes.
04

Replay is refused — the token is single-use

Try the same approved token again and it's gone. One approval authorizes exactly one execution.

tools-api · replay probe
$ tool.send_email { …, action_token:"apr-722076….<secret>" }   # second use
409 {"error":"action token already consumed"}   // audit: replay_refused
What it proves: approval is not a reusable capability — it is bound to one action, once.
05

The approved execution — as one linked trace

Pulled live from the Tempo API: the retry decomposed across four services. Note the approval.consume → POST /consume gate — the hash check and single-use consumption — happening before email.send.

localhost:3001 — Grafana · Explore → Tempo · { prokura.flow = "C" }
What it proves: the verification gate is on the execution path — reconstructable from telemetry, not taken on trust.

What this flow guarantees

  • ✓The approved action is the one the server stored — the human never sees agent-authored text.
  • ✓Approval yields a single-use token, hash-bound to the exact payload; replay is refused.
  • ✓The action runs exactly once, and only after a human decision relayed via CIBA.

Decisions: CIBA via Keycloak's built-in channel ADR-0006; notify-only, decisions only through the authenticated surface ADR-0007; single-use action tokens ADR-0008.
