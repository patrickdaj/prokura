Surface · the MCP server

An authorization server a real agent connects to

The chain isn't driven by a library — it's driven by a standard MCP client that discovers the server, registers itself, logs the user in, and calls tools. Keycloak is the MCP authorization server; the MCP server never forwards the inbound token downstream.

Keycloak as MCP ASRFC 9728 · 8414 · 7591no passthrough
01

Cold start → discover → register → log in

A cold POST /mcp returns a 401 whose WWW-Authenticate points at RFC 9728 metadata naming Keycloak. The client registers dynamically and runs OAuth 2.1 + PKCE, landing an aud=mcp-server token.

:8140/mcp · handshake
401 WWW-Authenticate: Bearer resource_metadata="…/.well-known/oauth-protected-resource"
# PRM → authorization_servers: [ …/realms/prokura ]
# DCR (RFC 7591) → OAuth 2.1 + PKCE →  token.aud = "mcp-server"
tools/list → [ get_provider_token, send_email, rag_search ]
What it proves: the exact handshake a real MCP client (Claude among them) performs — no operator involved.
02

Registration confers no trust

Any client can register — that's the point of DCR. A freshly-registered client gets an aud=mcp-server token and nothing else: reaching a user's grant still needs the can_use consent tuple.

gate check
fresh DCR client → token.aud=mcp-server   // registered
get_provider_token(acme) → broker → 403 denied_consent   // no can_use tuple
// consent — not registration — is the gate
What it proves: the untrusted DCR client can't self-elevate; consent and approval are the real gates.
03

No token passthrough — each tool re-exchanges

The inbound MCP token is addressed to mcp-server. Each tool exchanges it (RFC 8693) for the specific downstream audience it needs; presenting the raw MCP token downstream is refused.

exchange, per hop
get_provider_token → exchange → aud=token-broker
send_email        → exchange → aud=agent-tools-api
rag_search        → exchange → aud=rag-server   // sub preserved, azp=mcp-server
# inbound mcp-server token presented directly to any of them → 403
What it proves: the inbound token never leaks past the MCP boundary.

What this surface guarantees

  • ✓A cold request returns 401 + resource metadata naming Keycloak (RFC 9728).
  • ✓A dynamically-registered client completes OAuth 2.1 + PKCE; a wrong-audience token is refused.
  • ✓The inbound MCP token is never forwarded — every hop is a fresh exchange.

The decision to make the MCP server the headline — and the documented RFC 8707 gap (audience bound by a client scope) — is ADR-0013.
