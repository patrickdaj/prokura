Flow B · brokering deep-dive

Third-party access, without the agent ever holding a secret

The agent needs a token for a third-party provider (acme). It asks the broker — and gets back a short-lived access token only. The long-lived refresh credential lives in OpenBao and never leaves; every hand-out is gated by consent and an authorization check. Screens below are captured from the running stack.

01

The agent calls get_provider_token — and gets a bounded token

Through the MCP tool, the agent asks the broker for an acme token. The broker re-exchanges the agent's identity, checks consent, and returns an access token capped at 900 s — with no refresh token in the response.

tool: get_provider_token(provider="acme")
{ "access_token": "eyJhbGciOiJSUzI1NiIs…",
  "expires_in": 900,           // ≤ 900 s, always
  "scope": "openid email profile" }
// refresh_token: ABSENT — it never leaves OpenBao
What it proves: the agent is handed a capability that self-expires; it never sees the durable credential.
02

Where the durable credential actually lives — OpenBao

The provider refresh credential was acquired via Keycloak account-linking and written to OpenBao by the broker (the sole writer). Here it is at secret/grants/alice/acme — the values are masked by the vault; the agent, and this page, only ever see dots.

localhost:8200 — OpenBao · secret/grants/alice/acme
What it proves: the refresh credential is sealed in OpenBao (kind: refresh_token), scoped to the broker's policy — not in the agent, not in a token, not on this page.
03

No passthrough — the inbound token is refused downstream

What if the agent just forwards its inbound MCP token straight to the broker? It bounces — the broker only accepts a token minted for its own audience. Each tool re-exchanges; nothing is forwarded.

broker · inbound-token passthrough probe
$ POST :8110/v1/tokens/acme   Authorization: Bearer <aud=mcp-server>
403 {"error":"wrong audience: aud=['mcp-server'] does not include 'token-broker'"}
What it proves: holding the inbound token grants nothing downstream — the confused-deputy defense at the broker boundary.
04

Inside the broker — authorize, read, refresh, rotate

Pulled live from the Tempo API: the broker's slice of one delegated action. Before it returns anything it runs an fga.check (→ OpenFGA), reads the grant from OpenBao, refreshes at the provider, and rotates the stored secret — the whole custody chain, in one trace.

What this flow guarantees

  • ✓Refresh credentials exist only in OpenBao (broker token scoped to secret/data/grants/*).
  • ✓The agent receives access tokens only, scope-checked against the grant, capped at 900 s.
  • ✓Every hand-out passes an fga.check; the inbound token is never forwarded (no passthrough).

Decisions: acquisition via Keycloak linking ADR-0011; sole-writer can_use ADR-0001; per-agent consent ADR-0012.
