Surface · the authority console

One place to read the register and tear up the grant

Power of attorney is only tolerable if you can see who acts for you and revoke it in one click. The authority console is the principal's own signed-in page: every agent acting for you, the grants each can use, your approvals, your notification topic, and a live feed — plus revoke and "connect a provider". It adds no new authority: it relays your authority downstream by token exchange, with the broker still the sole writer. Every screen below is captured live.

01

Sign in → read your register

You log in on the console's own surface (Authorization Code + PKCE, the authority-ui client, a signed session cookie — no ?token= anywhere). It then shows, for you alone: the agents you operate, each with its consented grants and scopes.

localhost:8160 — your authority register
What it proves: the principal's scattered authority — agents, grants, approvals, topic — is aggregated behind one authenticated session, derived from service-held state, none from client-supplied identity.
02

Downstream is your authority, by exchange — never a service acting for nobody

The console holds no service credential that acts on authorization state and asserts no username out of band. For every read or action it exchanges (RFC 8693) your session token — as the authority-console client — into the exact audience it needs. The exchanged token preserves your subject, so downstream the owner is the verified token subject.

token exchange, per read/action
authority-ui login        → token.sub=alice  aud=[authority-console]  // exchangeable
exchange (authority-console) → aud=token-broker   sub=alice preserved   // consents, revoke, import
exchange (authority-console) → aud=approval       sub=alice preserved   // approvals, topic
// the broker sees owner = verified subject — the same M7 write-guard, reused
What it proves: the console is a surface, not a new authority — a confused-deputy that asserts identity out of band is exactly what this refuses.
03

One click tears up the delegation

Clicking Revoke exchanges your token for aud=token-broker and calls the broker's revoke — the same code path and audit event as the M7 consent screen. The tuple is deleted, the register reflects it, and every other agent is untouched. Honest about latency: effect applies on the agent's next hand-out (instant is M9).

localhost:8160 — after revoking agent-app
verified by looking · the real sinks
$ revoke agent-app / acme   → exchange → broker POST /v1/consent/revoke
OpenFGA: can_use(agent:agent-app, grant:alice/acme)   → gone
agent-app next hand-out: POST /v1/tokens/acme        → 403 not_consented
loki: broker_audit decision=consent_revoked user=alice agent=agent-app azp=authority-console
What it proves: revoke is real — tuple gone in OpenFGA, a consent_revoked audit line in Loki with you as the acting user, and the revoked agent's next request refused.
04

Connect a provider — a real person links, end to end

"Connect a provider" routes you into Keycloak account linking (kc_action=idp_link) in your own browser; you log into the provider, and on return the console imports the grant with your exchanged token. No admin API, no demo driver — closing Flow B's last gap.

localhost:8160 — connect a provider
the linking ceremony
$ GET /api/link/acme        → kc_action=idp_link:acme  // your browser
… provider login … link     → kc_action_status=success
/api/link/callback          → exchange → broker POST /v1/grants/acme/import  // your token
register.grants += acme       // no admin API, no demo driver ran
localhost:8160 — back on the register
What it proves: a real person routes themselves into idp_link and the grant lands imported under their own identity — the last correct-party gap, closed.
05

Notification onboarding — learn your topic

The console shows your unguessable ntfy topic and a subscribe affordance (URL + QR), read from the approval service with your user-bound token. The topic salt never leaves that service, and the topic stays notify-only — knowing it grants nothing (ADR-0007).

localhost:8160 — notifications
What it proves: the last scattered piece — "where do my approval pushes go?" — is answered on the same page, without the topic derivation ever leaving the approval service.

What this surface guarantees

  • ✓One signed-in page shows only the principal's own agents, grants, approvals, topic and activity — cross-principal data is never reachable.
  • ✓Every downstream call carries the user's exchanged, subject-preserving token — no service account acting for nobody, no out-of-band username.
  • ✓Revoke converges on the broker (the sole tuple writer) and the same audit event as the consent screen; the console writes no authorization state.
  • ✓A real person links a provider from the console — no admin API — closing the last correct-party gap.

The console as an aggregating trusted surface that relays the principal's own authority by token exchange (no new write authority) is ADR-0023.
