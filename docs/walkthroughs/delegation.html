Flow A · delegation deep-dive

One login becomes a scoped, single-audience token

An agent starts empty-handed. To act for Alice it must send her through a real login and an explicit consent — and what it gets back is a token that says sub=alice, azp=agent, addressed to exactly one audience and valid for minutes, not forever. Every screen below is captured from the running stack.

01

The agent connects the way any MCP client would — and is challenged

No token, no shortcut. The agent hits the MCP server, gets a 401 pointing at the authorization server, discovers metadata, and registers itself dynamically (DCR). Only then can it start an OAuth 2.1 + PKCE login.

MCP handshake
$ POST :8140/mcp        # no Authorization header
401 WWW-Authenticate: Bearer resource_metadata="…/.well-known/oauth-protected-resource"
$ POST :8180/realms/prokura/clients-registrations/openid-connect
201 { "client_name": "Claude (MCP client)", "token_endpoint_auth_method": "none" }
What it proves: the client is unprivileged until a human authenticates — there is no operator key in the loop.
02

The delegation request — a real login page

The agent sends Alice to Keycloak's own login (PKCE-protected). This is Prokura's realm, branded, with a mock external IdP option — the genuine article, not a recreation.

localhost:8180 — Sign in to Prokura
What it proves: the human authenticates directly with the identity provider — the agent never sees the password.
03

The consent — Alice grants the agent authority, in plain words

Before any token is minted, Keycloak shows Alice exactly what she is granting. This is the delegation: a human, looking at named privileges, clicking Yes.

localhost:8180 — Grant access
What it proves: authority is delegated by an informed human decision, scoped to declared privileges — not assumed by the agent.
04

Granted → a scoped, single-audience, short-lived token

Alice's Yes returns an authorization code to the agent, which exchanges it (PKCE) for the access token below. Note the three things that make it safe: it carries her identity, it is addressed to one audience, and it expires in 15 minutes.

127.0.0.1:9876 — agent redirect
decoded access token (real claims)
{
  "sub"  : "alice",              // the user — delegation is honest about who
  "azp"  : "Claude (MCP client)",// the agent that is acting
  "aud"  : "mcp-server",         // exactly ONE audience
  "scope": "openid profile mcp-audience",
  "exp"  : iat + 900            // ~15 min — empowered, but only for so long
}
What it proves: the acting identity is user-via-agent; the token is addressed to a single resource and self-expires.
05

A foreign-audience token is refused

Take that aud=mcp-server token and present it to a different resource — the broker — and it bounces. Holding a token isn't enough; it must be this resource's token.

broker · wrong-audience probe
$ POST :8110/v1/tokens/acme   Authorization: Bearer <aud=mcp-server>
403 {"error":"wrong audience: aud=['mcp-server'] does not include 'token-broker'"}
What it proves: the confused-deputy defense (F2), enforced at every service boundary.
06

Watch the delegated identity flow — as one linked trace

Once Alice's token exists, every hop it drives shares one trace id. What this flow guarantees

  • ✓Authority is granted by an informed human consent, not assumed by the agent.
  • ✓The token carries the original sub, the agent azp, and only requested scopes.
  • ✓It is addressed to exactly one audience; a foreign-audience token is refused everywhere.
  • ✓Every agent-held token is capped at ≤ 900 s.

The audience-per-resource rule is ADR-0002; the TTL honesty rule is ADR-0003.
