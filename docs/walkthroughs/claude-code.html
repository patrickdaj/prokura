Before you start

Prerequisites

  • ▹The stack is up: docker compose up -d.
  • ▹Seed the demo state once — python demo/run_demo.py links the acme grant, seeds the operator, and records the agent's consent (Flows B–D rely on this existing).
  • ▹Claude Code is installed and you can run claude. Log in to Keycloak as alice / alice (and later bob / bob).
Prokura's consent "agent" is always mcp-server (every tool re-exchanges the inbound token as that client), so the consent the demo seeds applies no matter which MCP client — including Claude Code — connects. You are not re-consenting per client for the third-party grant.
Where the Tempo filters below go: open Grafana at localhost:3001 → Explore → pick the Tempo data source → TraceQL query box, and paste the { .prokura.flow = "…" } filter shown in each Verify. Only tool calls stamp a flow — get_provider_token→B, send_email→C, rag_search→D — and health-check noise carries no flow tag, so each filter lands on exactly one clean end-to-end trace. Add && .prokura.user = "alice" (or "bob") to narrow to one person.
A

Flow A — Delegation: connect, and the OAuth handshake is the flow

Adding the server and authenticating is Flow A — discovery → dynamic registration → OAuth 2.1 + PKCE → a delegated aud=mcp-server token. No OAuth flags needed; Claude Code discovers everything from the server's metadata.

your shell
# add Prokura's MCP server — OAuth is automatic (RFC 9728 discovery + DCR + PKCE)
$ claude mcp add --transport http prokura http://localhost:8140/mcp

# authenticate — opens your browser to Keycloak (or run /mcp inside a session)
$ claude mcp login prokura
#   → sign in as alice / alice

# confirm it connected and see the tools
$ claude mcp list           # prokura → ✔ Connected · 3 tools
$ claude mcp get prokura     # get_provider_token, send_email, rag_search

Verify

  • ✓Your browser really opened Keycloak's login — the agent never saw the password.
  • ✓claude mcp list shows prokura · Connected with the three tools.
  • ✓The handshake itself emits no Prokura trace — discovery, DCR and PKCE run in Keycloak and the server's OAuth endpoints, which aren't on Prokura's telemetry. That's expected: the delegated aud=mcp-server token becomes visible in a trace the first time you use it — the keycloak.mcp_exchange span inside Flow B ({ .prokura.flow = "B" }), where you can confirm aud=mcp-server and exp ≤ 900 s.
What it proves: a real, independent MCP client obtains delegated authority through the standard handshake — nothing Prokura-specific on the client side. → Flow A deep-dive
B

Flow B — Brokering: ask for a third-party token

Tool use is natural language — Claude picks the right tool. Ask it for an acme token.

claude — in session
> Use the prokura tools to get me a provider access token for "acme".

Verify

  • ✓The result carries expires_in: 900 and no refresh_token.
  • ✓Open OpenBao at localhost:8200 (dev root token prokura-dev-root) → secret/grants/alice/acme holds the refresh credential (masked) — the durable secret Claude never receives.
  • ✓In Tempo, filter { .prokura.flow = "B" } — the waterfall shows tool.get_provider_token → keycloak.mcp_exchange → the broker's fga.check → OpenFGA, openbao.read_grant, and provider.refresh, all inside the one call.
What it proves: the agent is handed a bounded capability; authorization and secret custody happen server-side. → Flow B deep-dive
C

Flow C — Approval: ask it to send an email, then approve as a human

Sensitive actions pause. Claude's first attempt is refused; you approve the server-stored payload out-of-band, then it runs once.

claude — in session
> Use prokura to send an email to board@prokura.local,
  subject "Q3 board update", body "Revenue up 12% QoQ."

Verify

  • ✓Claude reports the first attempt was refused pending approval (a 428 with a reference) — it does not just send.
  • ✓You get an ntfy push (localhost:8090) carrying a deep link — open that (or localhost:8120/login?ref=<ref> using the 428's reference), which bounces you through Keycloak → sign in as alice / alice and lands on the specific request. Don't open bare /approvals — with no session and no ref it just says "No approval to review". (M7: the surface has a real session — no token in the link.) Confirm it shows the exact to/subject/body the server stored, and click Approve.
  • ✓Ask Claude to retry → it sends. The mail appears in Mailpit at localhost:8025.
  • ✓A second use of the same approval is refused (409, single-use).
  • ✓In Tempo, filter { .prokura.flow = "C" } — the refused first attempt renders red (a denied span carrying the approval_required decision), and the approved retry decomposes across mcp → approval → tools; the Tempo→Loki jump on any span lands on the matching audit lines.
What it proves: a human approved the action the server holds — not agent text — and it ran exactly once. → Flow C deep-dive
D

Flow D — FGA RAG: the same query, two users, two answers

Ask the adversarial question as alice, then re-authenticate as bob and ask again.

claude — in session (as alice)
> Use prokura's rag_search to answer:
  "When does the Meridian acquisition close?"
your shell — switch users
$ claude mcp logout prokura      # clear alice's stored token
$ claude mcp login prokura       # sign in as bob / bob
# then ask the identical question again in a session

Verify

  • ✓alice's answer names Meridian (she is a viewer of secret-roadmap).
  • ✓bob's identical query never mentions Meridian — the same top hit is filtered out.
  • ✓In Tempo, filter { .prokura.flow = "D" } for both searches — or narrow to one person with { .prokura.flow = "D" && .prokura.user = "bob" }. Each trace shows fga.batch_check evaluated as the querying user; the Tempo→Loki jump reaches that search's rag_audit … candidates=4 allowed=3 (bob's shows one fewer allowed).
What it proves: retrieval is authorized as the human, not the agent — the confused-deputy is dead. → Flow D deep-dive

Read carefully — this is a validation runbook

Honest caveats & likely friction

This handshake between Claude Code and Prokura has not yet been exercised end-to-end — proving it is the point. Expect to hit some of these:

  • ▹Keycloak must accept Claude Code's redirect. Claude Code dynamically registers its own client with a loopback callback. If login fails at the redirect, pin the port with --callback-port <port> and/or check the realm's client-registration redirect policy.
  • ▹The explicit "act on your behalf" consent screen is applied per-client at capture time (demo/capture/flow_a.py). A fresh DCR client (Claude Code's) will show Keycloak's login — the authorization-code issuance is still the delegation — but not necessarily the consent detail, until the realm is configured to require it (see the "persist the consent-screen scope" hardening item in the roadmap).
  • ▹The approval UI currently authenticates via a token in the URL (a dev shortcut); the intended path is opening the ntfy deep link inside an authenticated Keycloak session. See the note on Flow C.
  • ▹Switching users needs claude mcp logout prokura first — OAuth credentials are stored per user.
  • ▹Headless (claude -p) can't open a browser — authenticate interactively once (claude mcp login), then -p runs reuse the stored, auto-refreshed token.
Findings from this exercise feed straight back into the roadmap's Drive it with a real MCP client and Hardening items.
